# ASOBooN Model — MUST Requirements

この文書はASOBooN受付・呼出システムの非交渉要件を定義する。以下を満たさない設計・実装は採用しない。

## 1. ミニアプリからの予約
- ASOBooNミニアプリから予約できること。
- 位置情報・館内判定・NFC等を予約条件にしない。どこからでも予約可能とする。
- 予約確定時にAirWAITへ正式な予約/受付として登録されること。
- 予約成功時に `receiptNo` と、取得可能な場合は `reserveId` / `shortUrl` を保存する。
- 端末には受付番号・利用日・利用回・人数・状態照会用情報を保存し、再訪時に復元できること。

## 2. 前日19:00から翌日分を予約
- 翌日の予約は前日19:00から受付開始する。
- 19:00より前は翌日枠を確定できない。
- 仕様書の `reserve/create` には予約日パラメータがないため、AirWAIT側で翌日/時間指定予約を作成する正式手段を確認してから本番実装する。
- 確認できないまま「19:00以降のcreateを翌日扱い」と推測して運用しない。

## 3. AirWAIT側は枠を常設、日別制御はミニアプリ側
- ASOBooNで使用するAirWAIT待ち項目/予約枠は原則としてAirWAIT側に常設する。
- 曜日、特定日、繁忙日、イベント日などによる「どの回を予約可能にするか」はミニアプリ側の営業日カレンダーで制御する。
- AirWAIT側の待ち項目名の文字列解析だけで営業枠を決めない。`waitTypeId` を明示設定する。
- WEB予約用枠とミニアプリ受付用枠は識別可能な状態を維持する。

## 4. 自動呼出はAirWAIT標準機能を使わずASOBooN側で実行
- AirWAITの標準自動呼出はOFFで運用する。
- ASOBooN側が入場開始時刻、呼出中件数、予約種別、受付順を判断して呼出APIを実行する。
- 同一入場回のWEB予約＋ミニアプリ予約を合わせ、呼出中は合計最大10組を基本とする。
- 呼出中が減れば次の予約を自動補充する。
- iPad/ブラウザが閉じていても自動呼出が継続するサーバー実行方式とする。
- `Txxx`、`Fxxx`、通常番号を別予約として扱う。
- WEB/時間指定予約の `reserveId` 取得方法が確定するまでAUTOを本番開放しない。

## 5. ミニアプリ内のマイ予約
- ミニアプリで予約した直後に受付番号を端末へ保存する。
- 予約後は「マイ予約」から以下を確認できること。
  - 受付番号
  - 利用日
  - 予約した回
  - 人数
  - 現在状態（待ち中 / 呼出中 / 対応中 / 完了 / 取消）
  - 入場開始予定時刻
  - 呼出時間の目安
- 呼出中になったら視覚的に明確な表示へ変える。
- 同一営業日の重複受付を防止する。

## 6. 呼出時間の目安
- AirWAITの状態を正本として、ASOBooN側で目安時間を算出する。
- 開始前は「○:○○ごろから呼出予定」を表示する。
- 開始後は、同一入場回の現在呼出中件数・自分より前の待ち件数・直近の案内ペースから推定する。
- 推定値であることをUI上で明示し、確定時刻とは表現しない。

## 7. 正本と責務
- 予約・受付状態の正本はAirWAIT。
- ASOBooN側は「日別枠制御」「端末保存」「状態表示」「呼出目安」「自動呼出」「運用監視」を担当する。
- APIキーなどの秘密情報はブラウザ/GitHubへ置かない。
- 受付APIを中継する場合も、業務ロジックを抱え込む重いGASではなく、秘密情報を保護する薄いAPI層を優先する。

## 本番前のAirWAIT確認事項
1. 外部APIから翌日/時間指定予約を作成する正式な方法。
2. WEB/時間指定予約の `reserveId` を取得する正式な方法。
3. `reserve/call` の現行エンドポイントと `callingMethodType`。
4. 前日19:00運用とAirWAIT側の営業日切替の関係。

この4点が確定するまでは、該当機能を推測で開放しない。
