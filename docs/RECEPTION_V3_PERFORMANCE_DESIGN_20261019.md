# ASOBooN LINEミニアプリ｜体感5秒を解消する受付V3設計（非公開）

**2026-10-19／日中は設計・模擬テストのみ**  
**本番（main・GitHub Pages・本番Worker・D1・AirWAIT・LINE Developers）変更禁止。営業時間中にマージ・デプロイしない。**

## 何が分かったか

10/19深夜の「0.86秒」は「`.v38-home` 要素が表示された時点」の合成条件下の時間であり、受付を実際に操作できるようになるまでの時間ではなかった。施設の実機では約5秒の体感が残っており、この差を埋める計測が必要。

既存実装で確認した、5秒の体感につながりうる待ち：
1. 初回のLINE SDK／`liff.init()`。公開HOMEは先に描画するが、LINEの利用許可待ちは短縮できない。
2. **受付画面に移ると初めて** `production-routes.js`（約148KB）、`production-routes.css`（約90KB）がロードされる。ホームを早くしてもタップ後のウォーターフォールが残る。
3. `miniapp-v2/shared/reception.js` の `boot()` は、`waitForLine()`、`D.getCurrent({force:true})`、`GET health + GET waitTypes` の三系統を `Promise.allSettled` で **全部待ってから** 受付枠を表示する。営業日を強制再取得しているためHOMEの成功キャッシュを活用しきれない。
4. 状態・残数の自動取得は別であり、ホーム描画だけの改善では受付の体感速度を解消できない。

## 目指す構成：FAST SHELL + VERIFIED COMMIT

```
       公式LINEから起動
           |
           +--[A] 最小HOME（既存の安全なQRハンドオフ維持）
           |
           +--[B] 次に開く「受付」画面のJS/CSSを先読み
           |       ※回線・端末負荷を観測し、低速通信なら強制しない
           |
           +--[C] キャッシュ済みの営業日を日付整合・鮮度確認の上で表示
           |
           +--[D] LINE認証・営業日最新検証・受付枠の有効性を並行取得
           |
         受付タップ
           |
        枠・人数フォームを即表示（未確定と明記）
           |
         最新の検証がそろったら [確定] を有効化
           |
        既存の本番Workerが本人確認・営業日・受付枠・所有者を再検証
           |
          AirWAIT発行 / 通知 / キャンセルは従来処理
```

### A. 画面は先に、確定判定は後

- 受付画面はネットワークと本人確認の完了前に描画してよい。ただし未確認の受付枠を「申込可能」と誤認させない。
- 料金・人数選択と案内は通信と独立。確認中には「枠を確認しています」と表示し、**受付確定ボタンは常に無効**。
- `canCreate` の必要条件：確認済みLINE本人認証、同一運用日の営業情報、最新の有効な受付枠、Workerのcreate可否、既存の重複受付防止状態、全入力バリデーション。いずれかが未確認ならfalse。
- すべての取得結果は「世代番号」で管理し、日付切替・画面移動・予約の連続タップ後に遅れて戻った結果が古いボタンを有効化しない。
- 19:00 JSTを跨いだ古い営業日や古い残数は再利用しない。

### B. 受付専用の小さなバンドルに分割

現行の`production-routes.js/css`は受付だけでなく呼び出し・駐車場・ガイドなど全部を含む。初回の「受付」タップで使うコードだけを専用バンドルに分離する。

- **受け付け用最小モジュール**（受付UI、人数ルール、送信時の本人確認・エラー表示）を先行配信。サイズ・gzip・端末負荷を計測。
- 呼び出し状況・タイマー・その他ガイドはそれぞれ初回遷移時に追加ロード。初回HOMEには不要なJS/CSSを含めない。
- 既存`ASOBOON_V2_ENSURE_ROUTE_ASSETS`互換の薄いルータを用意し、旧ブックマーク、QR、遷移、戻る操作を保持。
- `prefetch`／`modulepreload`の選択は実機で比較し、不要な二重ダウンロードを避ける。

### C. 読取専用「受付ブートストラップ」APIを検討

現状は `health` と `waitTypes` が別GETで、営業日とも別。Cloudflare側で、**読取専用の集約エンドポイント**の試作を行う。

- 返却候補：`operationalDate`、`businessType`、`isClosed`、`checkedAt`、受付枠の公開設定、`createEnabled`、`dataFreshUntil`、`version`。秘密情報、個人ID、LINEトークン、予約情報は含めない。
- 更新はサーバー側の定期取得＋D1に保存。データの期限切れ／不一致は`unverified`としてUIに示す。
- ブートストラップは表示用であり、予約作成時の本人認証・枠検証・通知の成功条件は一切緩めない。
- API障害時には既存の`health`／`waitTypes`をフォールバック。AirWAITへのリクエスト集中を起こさない設計を優先。
- **本番APIへの実装・デプロイは営業終了後の別レビュー**でのみ行う。現段階ではAPI設計と模擬サーバーだけ。

### D. 「本当に5秒」を測る。個人情報は記録しない

ユーザーの実感に近いイベントを分離する。開発／試験環境だけで `performance.mark` を使用。

| 指標 | 起点 → 終点 | 改善目標（仮） |
|---|---|---|
| HOME first meaningful | URL起動 → HOME主要操作が見える | p75 1.5秒未満 |
| Reception first usable shell | 受付ボタンタップ → フォームが動く | p75 0.5秒未満 |
| Verified selectable slots | タップ → 営業日／枠の検証済み表示 | p75 2秒未満 |
| Auth ready | LINE SDK要求 → `liff.init`成功 | 別枠で測る（上限保証しない） |
| Submit ready | タップ → 本人確認を含む全条件が満たされた | p75 3秒未満を目指すが実機で再評価 |

- 端末を**LINE内**で確認（通常ブラウザの数字で代用しない）。
- 初回・2回目、Wi‑Fi／4G、iOS／Androidを区別。
- 受付番号、ユーザーID、アクセストークン、GPS、個人の予約内容はログに送信しない。初期設定で外部計測送信OFF。
- サービス開始9:30・多人数同時アクセス（100／320）・19:00切替・通信断／遅延・キャンセル復帰・NFCスタンプを回帰テスト。

## 段階導入／切戻し条件

1. **営業時間内（現在）**：この専用ブランチで設計文書、模擬ブートストラップ、遅延／失敗テストのみ。mainにはマージしない。公式LINE・本番D1・公開Workerは変更しない。
2. **営業時間外**：許可を得てから検証済み最小バンドルをフロントに反映。実機でホーム、受付、呼出、予約復帰を確認。安全基準を満たさなければ切戻し。
3. **別途の検討**：読取専用APIのキャッシュ統合は、フロント効果とAirWAIT利用制限を測ってから別リリース。受付処理と同時に変更しない。
4. **絶対条件**：本人確認の迂回、受付枠の偽装、予約の二重発行、LINE通知の省略、キャンセル権限の緩和をしない。

## データが足りないこと

現時点で「5秒のうち何秒がLINE WebView起動で、何秒が受付ブート処理か」は**まだ未計測**。前回の約0.86秒は初期HOME表示の模擬試験で、体感5秒の否定材料ではない。これからの設計評価は**操作可能まで**と**受付確定の安全性**の両方で判断する。
