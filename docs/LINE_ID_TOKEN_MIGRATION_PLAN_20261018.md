# ASOBooN LINEミニアプリ｜IDトークン認証への段階移行案

**状態：設計のみ。現行本番には変更しない。**
基準：PR #107／コミット 541d8e7。既存のアクセストークン＋プロフィールAPIによる本人確認は稼働中。

## 目的・認証の基本

- 現行のLINEプロフィールAPI依存を減らし、画面操作・受付復元・本人キャンセルを安定化する。
- LINE MINI Appでopenidが許可されている場合、LIFFのgetIDTokenで得る生のIDトークンをサーバーに送り、LINE公式のIDトークン検証API（POST https://api.line.me/oauth2/v2.1/verify）で検証する。クライアントからユーザーIDやデコード済みプロフィール情報を受け取って本人として信頼しない。
- 検証済みのsubから従来と同じユーザーハッシュ（SHA-256、チャネルID＋コロン＋LINEユーザーID）を作る。同じチャネルで既存受付との連続性を試験する。
- LINEサービスメッセージの通知トークン発行には引き続きLIFFアクセストークンが必要。IDトークンだけには置き換えない。
- トークンをログ、URL、分析ツール、localStorage、DBに保存しない。HTTPSで渡す。
- 認証そのものを省略しない。失敗時は受付を発行しない。

## 対応が必要な全処理

| 処理 | 守るべき条件 |
| --- | --- |
| 受付発行（外側Worker＋Gatewayの2段階） | 受付番号の二重発行防止、同一requestIdの所有者チェック、既存D1データとの整合性 |
| 受付結果照会（requestStatus） | 本人以外は情報を読めない |
| 予約復元（recoverReservationSession） | 過去の受付を同じLINE利用者が引き継げる |
| 呼出・予約状況（reservationStatus） | セッションと本人の紐付けを維持 |
| 本人キャンセル（cancelReservation） | 別人の受付を取り消せない |
| LINE通知（serviceMessage） | LIFFアクセストークンによる通知トークンを維持 |

## 進め方：本番変更前に確認すること

1. **PublishedとDevelopingの両チャネル**でopenidが許可され、LINE実機でIDトークンが取得可能か確認する。未許可・nullのケースもテスト。
2. 開発版のみでLINE公式検証APIを使う新経路を作る。チャネルID、発行者、期限、subの妥当性と他ユーザーへのなりすまし防止を確認。
3. 現在のアクセストークン認証と新しいIDトークン認証で、同じユーザーが同じハッシュになることを確認する。旧受付を復元・キャンセルできないなら公開しない。
4. 受付発行、重複受付、期限切れ、当日の19時切替、呼出状況、LINE通知、キャンセルまで一通り動作試験。無権限・誤ったチャネルID・不正なトークンは受付0件。
5. 同じ通信条件で旧方式と新方式の中央値、p95、失敗率を比較する。IDトークン検証でもLINE API通信は必要。二重認証の削減までは速度改善を断言しない。
6. 新方式は機能フラグOFFが初期値。開発版→実機→段階公開→本番全体の順。問題時は旧方式に戻す。
7. 受付が動いている間は受付発行を停止するdarkモードのCloudflareデプロイを行わない。

## 混雑率％の表示方針（別件）

PR #106で削除した従来の％表示は、全枠の定員を350名固定としていたため、実際の枠と不一致になり得る。
復活するときは「館内混雑率」ではなく、正しくは**「受付枠の消化率」**。各回・各チャネルの正確な定員と残数から計算する。欠損値や古い情報なら0％とせず「確認中」を出す。見せ方は運営判断を確認してから変更する。
