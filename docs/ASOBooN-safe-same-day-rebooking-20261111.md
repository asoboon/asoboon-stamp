# ASOBooN｜終了後の当日再受付の安全化（2026-11-11）

## 結論
**AirWAITの元の受付番号・予約記録は一切削除しない。** 新しい受付は、保存された古い受付がAirWAITで明確に「案内終了（status=2）」または「取消（status=3）」であると直接確認できたときだけ発行する。LINEユーザー・営業日・AirWAIT内部予約ID・受付枠でサーバー側に結びつける。

## 背景
旧サーバーは `v2_user_day_claims.state=CONFIRMED` が残ると、利用者が新しい枠で申し込んでも古い番号を `alreadyExists` として返しやすかった。以前の「終了→待機中へ戻す」もあるため、単純なローカル番号削除・一定時間後削除は危険。

## 実装
- Gateway `claimUserDay` は、前の `CONFIRMED` 受付を保持する場合、AirWAITの保存済み受付枠で**キャッシュなしのAPI再読込**を実行。完全一致する元の番号が1つで status 2/3 と確認できた場合のみ、D1の本人日別Claimを条件付きの**atomic compare-and-swap** で新規受付処理へ切り替える（`request_id`・`reserve_id`・`receipt_no`・枠・元状態を全一致）。既存番号が待機中/保留/呼出対応中、不明、曖昧、未掲載、API障害の場合は解放しない。
- 以前に本人確認済みの `COMPLETED` が保存され、スタッフがその番号を「待機中」に戻した場合、新規受付前のAirWAIT照合で `CONFIRMED` に戻す。その後は**以前の番号のみ返す**。終了済みの証拠のある番号がAirWAIT一覧からアーカイブ済みの場合は、過去の信頼済み終了情報を尊重し再受付可能。読み取りエラー/不明なら安全側で新規発行せず停止。
- 以前のProduction Workerに残っていた、AirWAIT終了番号を見つけて **D1 ClaimをDELETEし、同じ受付作成を再送する処理** は廃止。サーバー側の一度限りの比較更新に一本化。AirWAITに対して取消・削除APIは呼ばない。
- アプリの受付画面で、もし既存の受付が有効なら「以前の受付番号（新規発行なし）」「新しい番号は発行していません」と表示。新規発行時のみ「受付完了」と案内。AirWAIT照合の失敗には日本語の説明を表示。
- 実際の再受付は、呼出ページに既存の「もう一度受付する」ボタンがある。新規予約は利用者自身が受付を行ったときだけ作成し、自動発行しない。

## 守ること
- **AirWAITの受付履歴は消さない**
- 案内済みから待機中に戻した場合は同じ番号を守り、重複発行を防ぐ
- 受付番号の数字は枠間で重複するため、数字のみで照合しない
- 別利用者の受付番号・予約IDを操作しない
- 通信エラー・不明・暫定値を終了と断定しない
- LINE本人認証、通知トークン、公開枠判定、価格、混雑予想320人=100%などは変更しない
- 取消と終了を履歴に保存する仕組み、後日の来場記録を妨げない
